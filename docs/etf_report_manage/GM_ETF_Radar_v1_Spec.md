## 1. 풀려는 문제 (v1)

테마 ETF 추천 리포트를 만드는 검증된 6단계 워크플로(시장 리서치 → 축출 → 밸류에이션·레드팀 → 테마 확정 → 상품 실사 → 리포트)가 있으나, **사람이 수동으로 4~5시간** 걸린다. v1은 이 과정을 **서버 파이프라인 + 관리자 검토 게이트 2개**로 반자동화해 **리드타임을 30분 이내(관리자 검토 시간)로 단축**한다.

## 2. 사용자 (v1)

| 역할 | v1에서의 행동 |
|---|---|
| **관리자 (Dr.GM 팀)** | 리포트 생성 실행, G1(테마 확정안) 검토·수정·재실행, G2(발행) 승인, 리포트 목록·뷰어 열람 |
| (고객/자문사) | **v1 범위 밖** — 배포·열람은 2·3차에서. v1의 발행은 "PDF 산출 + 관리자 열람"까지 |

**JTBD**: *"관리자로서, 매월 테마 ETF 리포트를 만들 때, 반복적인 리서치·정리 작업을 AI에 맡기고 판단이 중요한 지점(축출·레드팀·발행)만 검토하고 싶다. 그래야 4~5시간을 30분으로 줄이면서 품질은 유지할 수 있다."*

## 3. 기능 범위 (MoSCoW)

### Must (v1 필수)
- **M1. 리포트 생성 파이프라인** S1~S4 자동 실행 (Claude API + web_search)
  - S1 시장 리서치·롱리스트 → S2 축출 → S3 밸류에이션·레드팀 → S4 최종 테마 확정안
  - 각 STAGE는 구조화 JSON 산출 → 다음 STAGE 입력
- **M2. 게이트 G1 (관리자 검토)** — S4 결과(테마안 + 축출 사유 + 레드팀) 승인 / 수정 / S1부터 재실행
- **M3. 상품 실사 S5** — 테마별 ETF 실사(수익률·상위종목·배당·보수·AUM, 기준일 필수, 미확보=“확인 불가”)
- **M4. 리포트 렌더링 S6** — JSON → 리포트 MD → Dr.GM 규격 HTML → **PDF(weasyprint)**. 직전 리포트 존재 시 변경 요약 섹션
- **M5. 게이트 G2 (발행 승인)** — 미리보기 후 발행 → 리포트 상태 `published`, PDF 저장·열람 가능
- **M6. 관리자 콘솔 화면** — 리포트 목록(상태별), 생성 실행, G1 검토, G2 발행, 리포트 뷰어

### Should (여유 시)
- 파이프라인 진행 상황 실시간 표시(STAGE별 스트리밍/폴링)
- 직전 리포트 대비 변경 요약(테마 진입/이탈/순위 변동) 자동 생성
- 리포트 재실행 시 이전 산출물 버전 보관

### Could (선택)
- STAGE 프롬프트 버전 관리(레지스트리)
- 테마 개수·대상 시장(국장/미장) 파라미터 조절 UI

### Won't (v1 OUT — 후속 차수)
- ⛔ **시그널 추적조사(F3) 전체** — 시그널 레지스트리·수집기·신호등 판정 → **2차**
- ⛔ **R-CORE-1 발행↔시그널 자동등록** — F3가 존재해야 의미. v1 G2는 “발행”까지만. **2차에서 연동**
- ⛔ **이메일 발송(다이제스트/즉시 알림)** → **3차**
- ⛔ **자문사·고객 배포/열람 화면** — v1은 관리자 전용
- ⛔ **정기 자동 스케줄러(F2 월간 트리거)** — v1은 관리자 수동 실행만
- ⛔ **G3(🔴 알림 확인 게이트)** — 알림 자체가 3차

## 4. 화면 (v1 — 관리자 콘솔, `/content/etf-radar`)

| 화면 | 핵심 요소 | 흐름 |
|---|---|---|
| **S-1 리포트 목록** | 상태 배지(초안/G1대기/G2대기/발행됨), 생성일, 테마 수, [새 리포트 생성] 버튼 | 진입 첫 화면 |
| **S-2 생성 실행/진행** | 대상 시장·테마 수 파라미터, 실행 버튼, STAGE별 진행 표시 | 목록 → 생성 |
| **S-3 G1 검토** | 최종 테마안 + 축출 사유 + 레드팀 전문, [승인]/[테마 수정]/[재실행] | 파이프라인 S4 완료 시 |
| **S-4 G2 발행** | 리포트 미리보기(웹/PDF), 변경 요약, [발행 승인] | G1 승인 → S5·S6 자동 후 |
| **S-5 리포트 뷰어** | 발행 리포트 웹 뷰 + PDF 다운로드 | 목록 → 상세 |

**화면 흐름**: `S-1 목록 → S-2 생성 → (자동 S1~S4) → S-3 G1 → (자동 S5~S6) → S-4 G2 → S-5 뷰어`

## 5. 데이터 모델 (v1, 2차 확장 고려)

```
Report {
  id, title, status: DRAFT | G1_REVIEW | G2_REVIEW | PUBLISHED | ARCHIVED,
  target_markets: [KR, US], theme_count_requested,
  created_by, created_at, published_at,
  pdf_url, prev_report_id (변경요약용),
  // 2차 연동 예약 필드
  signals_registered_at (null in v1)
}
ReportStage {
  id, report_id,
  stage: S1|S2|S3|S4|S5|S6,
  output_json,          // 각 STAGE 구조화 산출물
  prompt_version, status: PENDING|DONE|FAILED, created_at
}
ReportTheme {                 // S4/S5 확정 테마 (2차 시그널의 부모가 됨)
  id, report_id, market, name, rank, logic,
  etf_products_json,          // 실사 결과(수익률·비중·보수 등)
  exit_conditions_json        // 이탈조건 초안 → 2차 F3에서 시그널로 파싱
}
```

> `ReportTheme.exit_conditions_json`은 v1에서 “측정 가능한 형태”로 저장만 하고, 2차 F3가 이를 Signal 스키마로 파싱한다(W3). v1에서 저장 규격을 지켜두는 것이 2차 연동의 핵심.

## 6. 기술 스택 (기존 인프라 재사용)

| 영역 | 선택 | 근거 |
|---|---|---|
| 백엔드 | FastAPI(Railway) + PostgreSQL(asyncpg) | 기존 스택 |
| LLM | **Claude API (web_search tool)** — S1~S5 messages 체인 | PRD 지정 |
| PDF | **weasyprint** (HTML→PDF), Dr.GM 규격 | Workflow 지정, 기존 리포트 엔진 재사용 |
| 디자인 SSOT | `gm-ppt-builder/SKILL.md`를 repo에 `design-reference`로 복사 후 참조 | Workflow §S6 |
| 상품 실사 데이터 | KRX/ETF 공개 데이터 (가능 시 기존 stock 인프라 재사용) | — |
| 프론트 | Next.js 16 + 기존 디자인 시스템(Navy) | 기존 스택 |
| 키 관리 | 기존 `user_api_keys`(Claude 키) 재사용 | 기존 |

**자동 결정(Mechanical)**: 리포트 상태 머신은 서버 단일 원천 / 각 STAGE 산출물은 JSON 컬럼 보관 / PDF는 서버 렌더 후 저장(URL 반환) / 파이프라인은 STAGE 독립 실행·실패 격리.

**판단 요청 해소됨(Taste)**: MVP 범위=리포트 제작만 / 리포트 트리거=관리자 수동 실행 / 인프라=백엔드 cron·기존 발송(단, v1은 발송 없음). — 오너 확정.

## 7. 비기능 요구 (v1 해당분)

- **비용 상한**: STAGE별 Claude 호출은 리포트당 1회씩, web_search 사용량 모니터링. 재실행 남용 방지.
- **재현성**: 각 STAGE 산출물·프롬프트 버전ID 기록(`ReportStage`).
- **장애 격리**: STAGE 실패 시 해당 리포트만 `FAILED`, 재실행 가능. 전체 앱 영향 없음.
- **데이터 시점 표기**: 모든 수치(실사)에 기준일 필수, 미확보=“확인 불가”.
- **컴플라이언스**: 리포트에 면책 문구 고정 삽입(정보 제공, 자문·매매지시 아님).

## 8. 성공 지표 (v1)

- 리포트 1건 생산 리드타임: 수동 4~5h → **관리자 검토 30분 이내**
- 파이프라인 완주율(S1~S6 무중단) ≥ 95%, STAGE 실패 시 재실행으로 복구 가능
- G1/G2 게이트에서 관리자가 수정·재실행할 수 있는 경로 100% 동작

## 9. 2차 연동 준비 체크 (v1에서 반드시 지킬 것)

- [ ] `ReportTheme.exit_conditions_json`을 “관측 가능한 형태”로 저장(예: “러-우 휴전 합의 보도” O / “지정학 완화” X)
- [ ] G2 발행 시점에 `published_at` 기록 → 2차 R-CORE-1 트리거 지점
- [ ] 리포트·테마 ID 체계를 2차 Signal의 `report_id` 외래키로 쓸 수 있게 안정적으로 유지
