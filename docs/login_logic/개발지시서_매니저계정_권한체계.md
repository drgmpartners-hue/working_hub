# **1. 배경과 목표**

## **1.1 현재 상태**

현재 Working Hub Manager는 대표 한 사람이 모든 데이터에 접근해
입력·수정·삭제하는 단일 사용자 전제로 만들어져 있다. 저장소의 프로젝트
메모리 파일에도 이 전제가 명시적인 설계 결정으로 기록되어 있다.

**기존 설계 결정 (본 지시서로 폐기)**

> .claude/memory/project.md — Key Decisions
>
> \- All employees same permissions (no RBAC needed)

본 지시서는 위 결정을 공식적으로 폐기한다. 구현 완료 시점에 해당 줄을
아래 문장으로 교체한다.

> \- 대표(owner) / 매니저(manager) 2단계 역할. 데이터 경계는
> clients.user_id 단일 규칙.
>
> \- 대표는 전체 접근 + 매니저 계정 대행 로그인 가능. 권한 판정은
> app/core/permissions.py 단일 지점.

## **1.2 달성하려는 업무 구조**

대표는 모든 매니저의 고객을 관여해 관리하고, 매니저는 자기 고객의
영업에만 집중한다. 매니저끼리는 서로의 고객을 볼 수 없다. 대표는 필요할
때 특정 매니저 계정으로 전환해 그 매니저가 보는 화면 그대로 작업을
대신해 준다.

| **주체**         | **볼 수 있는 것**                       | **할 수 있는 것**                                                                        |
|------------------|-----------------------------------------|------------------------------------------------------------------------------------------|
| 대표 (owner)     | 전 매니저의 고객·플랜·기록 전체         | 전체 조회·수정·삭제, 매니저 계정 생성/비활성, 담당자 이관, 대행 로그인, 공용 마스터 관리 |
| 매니저 (manager) | 본인이 담당하는 고객과 그 하위 데이터만 | 본인 고객 CRUD, 본인 업무 자료 CRUD, 공용 마스터는 읽기만                                |
| 고객 (포털)      | 본인에게 발급된 포털 토큰 범위          | 기존과 동일 (본 작업의 변경 대상 아님)                                                   |

## **1.3 이 설계를 택한 이유**

권한을 리소스별 CRUD 매트릭스로 세분화하면 역할 × 리소스 × 액션의 곱만큼
경우의 수가 늘어나고, 이후 기능을 추가할 때마다 권한 설계를 다시 해야
한다. 반면 본 설계는 판정 규칙이 하나뿐이다.

> 접근 가능 = (요청자가 대표) OR (대상 고객의 담당자 == 요청자)

고객 소유권 컬럼은 이미 존재하고(clients.user_id), 거의 모든 데이터가
고객에 매달려 있으므로 이 한 줄이 전체 데이터 경계를 결정한다. 규칙이
하나이므로 판정 함수도 하나로 모을 수 있고, 향후 기능 추가 시 개발자가
판단할 것은 "이 리소스는 어느 고객에 속하는가" 뿐이다.

| **설계 원칙** 권한 분기를 코드 곳곳에 if 문으로 흩뿌리지 않는다. 판정은 app/core/permissions.py 한 파일에서만 이뤄지고, 나머지 코드는 그 함수를 호출하기만 한다. |
|------------------------------------------------------------------------------------------------------------------------------------------------------------------|

# **2. 현황 진단 (실제 코드 기준)**

아래 내용은 저장소를 직접 조사한 결과다. 구현에 착수하기 전에 이 절을
먼저 읽고 전제를 확인할 것.

## **2.1 이미 갖춰져 있어 재사용할 것**

- **clients.user_id:** backend/app/models/client.py:22-24에
  ForeignKey("users.id", ondelete="CASCADE")로 이미 존재하며 index가
  걸려 있다. 담당자 컬럼을 새로 만들 필요가 없다.

- **소유권 조인 경로:** clients → client_accounts → portfolio_snapshots
  / portfolio_suggestions → call_reservations, 그리고 clients →
  customer_retirement_profiles → desired_plans / retirement_plans /
  pension_plans / interactive_calculations / investment_records 로 모든
  고객 데이터가 clients에 도달한다.

- **모범 패턴:** backend/app/api/v1/snapshots.py의
  \_verify_account_owner() / \_verify_snapshot_owner() (28~55행)가 이미
  조인으로 소유권을 검증한다. 이 패턴을 전체로 확장하는 것이 본 작업의
  핵심이다.

- **users.is_superuser:** 컬럼은 존재하나 코드에서 사용되지 않는다.
  의미가 불명확하므로 역할 판정에 재사용하지 않는다(5.1절 참조).

- **프론트 토큰 취급:** frontend/src/lib/auth.ts의
  authLib.getAuthHeader()가 localStorage의 access_token을 읽어 각 호출에
  수동으로 붙인다. axios 인터셉터가 없으므로, 대행 로그인 시
  localStorage 토큰만 교체하면 모든 화면에 즉시 반영된다.

## **2.3 구현 전에 정리해야 할 구조적 문제**

아래 세 가지는 권한 게이트를 얹기 전에 먼저 해소하지 않으면, 게이트를
달아도 구멍이 남거나 정상 기능이 깨진다. Phase 0에서 처리한다.

### **문제 A — deposit_accounts의 FK 부재**

models/deposit_account.py:23-27의 profile_id와 customer_id는
String(36)이며 ForeignKey가 없다. 모델 주석에 "FK 없이 유연하게"라고
적혀 있다. 조인으로 소유자를 역추적할 수는 있으나 정합성이 보장되지
않아, 고아 레코드가 있으면 권한 검사에서 조용히 누락된다.

- 조치: 마이그레이션 전 고아 레코드 조사 → 정리 → FK
  추가(ondelete="CASCADE"). FK 추가가 위험하다고 판단되면 최소한 검증
  쿼리를 Phase 8 회귀 테스트에 고정한다.

### **문제 B — investment_records의 customer_id 의미 혼재**

api/v1/investment_records.py의 customer_id 파라미터가 위치마다 다른 값을
가리킨다. Client.id, Client.unique_code,
CustomerRetirementProfile.customer_id 세 가지를 순차 시도하는 코드가
있고(93~112행 부근), 297행 목록 조회에서는
CustomerRetirementProfile.customer_id == current_user.id로 로그인 사용자
ID를 고객 ID 자리에 비교한다.

- 조치: 파라미터 의미를 clients.id 하나로 통일하고, unique_code 조회가
  필요한 화면은 별도 라우트로 분리한다. 통일 전에는 권한 검사를 정확히
  걸 수 없다.

### **문제 C — 프론트 401/403 처리의 부재**

axios 인터셉터가 없어 각 화면이 개별적으로 오류를 처리한다. 대행 로그인
세션 만료, 권한 없음(404 정책) 같은 새 응답이 추가되면 화면마다 다르게
깨진다.

- 조치: frontend/src/services/api.ts에 요청/응답 인터셉터를 도입해
  Authorization 헤더 자동 부착과 401·403 공통 처리를 일원화한다. 기존
  getAuthHeader() 직접 호출부는 유지해도 무방하나, 신규 코드는 인터셉터
  경로를 사용한다.

# **3. 설계 원칙 (위반 시 리뷰 반려)**

1.  **판정은 한 곳에서만 한다.** 권한 관련 조건문은
    app/core/permissions.py 안에만 존재한다. 라우터는 판정하지 않고
    호출만 한다.

2.  **서버가 관문이고 화면은 편의다.** 프론트에서 메뉴·버튼을 숨기는
    것은 UX 처리일 뿐이며, 숨겼다는 이유로 API 검사를 생략하지 않는다.

3.  **없는 것처럼 보이게 한다.** 권한 없는 리소스 요청에는 403이 아니라
    404를 반환한다. 403은 "그 ID가 존재한다"는 정보를 노출한다. 단, 역할
    부족으로 기능 자체를 못 쓰는 경우(매니저가 매니저 관리 API 호출)는
    403을 쓴다.

4.  **대행은 기록된다.** 대표가 매니저 계정으로 수행한 모든 쓰기 동작은
    실제 행위자와 연기 중인 계정을 함께 남긴다. 둘 중 하나만 남기는
    구현은 미완성으로 간주한다.

5.  **비밀번호를 공유하지 않는다.** 대행 로그인은 대표 토큰으로 발급받는
    전환 토큰 방식이며, 매니저의 비밀번호를 알거나 입력하는 흐름은 어떤
    경우에도 만들지 않는다.

6.  **기존 동작을 깨지 않는다.** 대표 계정 단독으로 쓰던 기존 화면은
    전부 그대로 동작해야 한다. 역할 컬럼 기본값과 마이그레이션 순서로
    이를 보장한다(12장).

# **4. 권한 모델 정의**

## **4.1 역할**

역할은 users 테이블의 role 컬럼 하나로 표현한다. 값은 'owner' 또는
'manager' 두 가지뿐이며, 중간 등급이나 커스텀 권한 세트는 만들지 않는다.
더 세분화하고 싶은 요구가 생기더라도 본 작업 범위에서는 추가하지 않는다.

## **4.2 데이터 3계층 분류**

모든 테이블을 아래 세 계층 중 하나로 분류한다. 신규 테이블을 추가할 때도
반드시 계층을 지정하고 그에 맞는 접근 규칙을 적용한다.

| **계층**       | **정의**                            | **접근 규칙**                       | **이관 대상**                 |
|----------------|-------------------------------------|-------------------------------------|-------------------------------|
| A. 고객 귀속   | clients를 최종 소유자로 하는 데이터 | 대표 전체 / 매니저는 담당 고객 것만 | 예 (담당자 변경 시 함께 이동) |
| B. 매니저 개인 | 매니저 본인의 업무 자료             | 대표 전체 / 매니저는 본인 것만      | 아니오 (원 소유자에 잔류)     |
| C. 전사 공용   | 회사 차원의 마스터·설정             | 전원 읽기 / 쓰기는 대표만           | 해당 없음                     |

### **계층 A — 고객 귀속 (담당자 이관 시 함께 이동)**

| **테이블**                                       | **소유권 도달 경로**                                    |
|--------------------------------------------------|---------------------------------------------------------|
| clients                                          | clients.user_id (기준점)                                |
| client_accounts                                  | client_id → clients                                     |
| portfolio_snapshots / snapshot_holdings          | client_account_id → client_accounts → clients           |
| portfolio_suggestions                            | account_id → client_accounts → clients                  |
| call_reservations                                | suggestion_id → portfolio_suggestions → … → clients     |
| customer_retirement_profiles                     | customer_id → clients.id                                |
| desired_plans / retirement_plans / pension_plans | profile_id → customer_retirement_profiles → clients     |
| interactive_calculations / investment_records    | profile_id → customer_retirement_profiles → clients     |
| deposit_accounts / deposit_transactions          | profile_id·customer_id → (FK 없음, 문제 A 참조)         |
| message_logs                                     | client_id → clients (user_id는 발송 당시 기록으로 유지) |

### **계층 B — 매니저 개인 자료 (이관하지 않음)**

아래 테이블은 이미 user_id를 보유하고 있으므로 소유자 판정이 단순하다.
담당 고객이 다른 매니저에게 넘어가도 이 자료는 원 작성자에게 남는다.

- commission_calculations / commission_details — 수당 정산 결과

- content_projects / 하위 산출물 — 콘텐츠 제작물

- portfolio_analyses — 포트폴리오 분석 기록

- stock_recommendations 및 stock.py의 user_id 보유 테이블

- sms_templates — 개인 문자 템플릿

- field_options — 개인 드롭다운 설정

- user_api_keys — 개인 API 키 (대표도 평문 조회 불가, 5.4절)

### **계층 C — 전사 공용 (쓰기는 대표만)**

- product_master, wrap_accounts, product_select_options,
  product_name_changes — 상품 마스터

- recommended_portfolios / recommended_portfolio_items — 전 고객 공통
  추천 템플릿

- brand_settings, ai_api_settings, app_settings — 브랜드·AI·앱 설정

- stock_metrics, market_analysis_cache, crawling 관련 — 시장 데이터 캐시

| **주의** 계층 C의 GET은 매니저에게도 열어 두어야 한다. 매니저가 상품 마스터를 읽지 못하면 포트폴리오 제안 화면 자체가 동작하지 않는다. 차단하는 것은 POST·PUT·PATCH·DELETE뿐이다. |

## **4.3 권한 판정 규칙 (의사코드)**

> \# 계층 A
>
> allow = (actor.role == "owner") or (client.user_id == actor.id)
>
> \# 계층 B
>
> allow = (actor.role == "owner") or (row.user_id == actor.id)
>
> \# 계층 C
>
> allow_read = True \# 인증된 사용자 전원
>
> allow_write = (actor.role == "owner")

여기서 actor는 "실효 사용자(effective user)"다. 대표가 매니저 계정으로

# **7. 대행 로그인 (계정 스위치)**

## **7.1 토큰 설계**

현재 토큰은 {"sub": user_id, "exp": ...} 구조이며 만료가
7일이다(core/security.py의 ACCESS_TOKEN_EXPIRE_MINUTES). 대행 토큰은
여기에 두 개의 클레임을 추가하고 만료를 짧게 가져간다.

| **클레임** | **값**         | **설명**                            |
|------------|----------------|-------------------------------------|
| sub        | 매니저 user id | 실효 사용자. 모든 권한 판정의 기준  |
| act        | 대표 user id   | 실제 행위자. 일반 토큰에는 없음     |
| imp        | true           | 대행 세션 표식 (프론트 배너 판단용) |
| exp        | 발급 + 2시간   | 일반 토큰(7일)보다 훨씬 짧게        |

create_access_token()은 현재 subject 하나만 받으므로, 추가 클레임을 받을
수 있도록 확장한다. 기존 호출부의 동작은 바뀌지 않아야 한다.

> \# backend/app/core/security.py
>
> def create_access_token(
>
> subject: str \| Any,
>
> expires_delta: timedelta \| None = None,
>
> extra_claims: dict \| None = None, \# 추가
>
> ) -\> str:
>
> ...
>
> to_encode = {"exp": expire, "sub": str(subject)}
>
> if extra_claims:
>
> to_encode.update(extra_claims)
>
> return jwt.encode(to_encode, settings.SECRET_KEY, algorithm=ALGORITHM)

# **9. 담당자 이관**

## **9.1 동작 원리**

계층 A의 모든 데이터는 clients에 매달려 있으므로, clients.user_id 하나를
바꾸면 하위 데이터가 전부 따라 이동한다. 별도의 대량 UPDATE는 필요 없다.
이것이 4장의 소유권 모델을 단일 컬럼으로 정한 실질적 이득이다.

## **9.2 API**

| **메서드 · 경로**                            | **요청 본문**           | **동작**                                      |
|----------------------------------------------|-------------------------|-----------------------------------------------|
| POST /api/v1/clients/{client_id}/transfer    | { to_user_id, reason? } | 단건 이관                                     |
| POST /api/v1/managers/{user_id}/transfer-all | { to_user_id, reason? } | 해당 매니저의 전 고객 일괄 이관 (퇴사 처리용) |
| GET /api/v1/clients/{client_id}/transfers    | —                       | 해당 고객의 이관 이력                         |

전 라우트에 require_owner()와 forbid_while_impersonating()을 적용한다.
일괄 이관은 단일 트랜잭션으로 처리하고, 건수가 많을 경우를 대비해 배치
커밋 단위를 정한다.

## **9.3 이관 시 함께 처리할 것**

1.  **message_logs.user_id는 바꾸지 않는다.** 발송 당시의 실제 발송자를
    보존해야 하기 때문이다. 대신 message_logs 조회 권한은 user_id가
    아니라 client_id 기준으로 판정하도록 message_logs.py와
    messaging.py를 수정한다(6.4절 12번 작업). 이 변경을 빠뜨리면 이관 후
    새 담당자가 과거 문자 이력을 보지 못한다.

2.  **계층 B 자료는 이동하지 않는다.** 수당 정산·콘텐츠·분석 기록은
    작성자 본인의 업무 산출물이므로 원 소유자에게 남는다.

3.  **field_options(개인 드롭다운 설정)는 이동하지 않는다.** 다만 새
    담당자의 설정에 없는 값이 고객 데이터에 들어 있을 수 있으므로,
    화면에서 저장된 값이 사라지지 않고 표시되는지 확인한다.

4.  **client_transfers와 audit_logs에 모두 기록한다.**
    action="transfer", resource_type="clients", client_id=대상 고객.

5.  **이관 대상 매니저 검증.** to_user_id가 존재하고 is_active이며
    role이 manager 또는 owner여야 한다. 비활성 계정으로 이관하면 고객이
    접근 불가 상태가 된다.

## **9.4 퇴사 처리 표준 절차**

매니저 비활성화와 고객 이관은 반드시 이 순서로 수행하며, 화면에서도 이
순서를 강제한다.

1.  대표가 /admin에서 해당 매니저의 담당 고객 수를 확인한다.

2.  transfer-all로 고객을 다른 매니저(또는 대표 본인)에게 넘긴다.

3.  담당 고객 0건이 된 것을 확인한 뒤 is_active=False로 전환한다.

4.  담당 고객이 남아 있는 상태에서의 비활성화 요청은 409로 거부하고,
    이관을 먼저 하도록 안내한다.

# **10. 감사 로그**

## **10.1 기록 대상**

- GET을 제외한 모든 요청 (POST·PUT·PATCH·DELETE) — 성공·실패 모두

- 대행 시작·종료

- 로그인 성공·실패, 비밀번호 변경

- 주민번호 복호화 조회 (GET이지만 예외적으로 기록)

- 담당자 이관, 매니저 계정 생성·비활성

일반 GET 조회는 기록하지 않는다. 기록량이 폭증해 정작 필요한 쓰기 이력을
찾기 어려워지기 때문이다.

## **10.2 구현 방식**

두 층으로 구현한다. 미들웨어로 전수 기록의 바닥을 깔고, 중요한 동작에만
의미 있는 세부 정보를 덧붙인다.

> \# 1층: app/main.py에 미들웨어 등록 — 누락 없는 기본 기록
>
> @app.middleware("http")
>
> async def audit_middleware(request: Request, call_next):
>
> response = await call_next(request)
>
> if request.method in ("POST", "PUT", "PATCH", "DELETE"):
>
> \# request.state에 라우트가 심어둔 ctx / resource 정보를 읽어 기록
>
> await write_audit_log(request, response)
>
> return response
>
> \# 2층: 서비스 계층에서 중요한 동작에 상세 정보 부착
>
> await audit(ctx, action="delete", resource_type="clients",
>
> resource_id=client.id, client_id=client.id,
>
> payload_summary={"name": client.name})

| **필수 요건** actor_user_id와 effective_user_id를 항상 함께 기록한다. "매니저A가 삭제함"이 아니라 "대표가 매니저A 계정으로 들어가서 삭제함"으로 남아야 분쟁 시 실제 행위자를 가릴 수 있다. 하나만 기록하는 구현은 감사 로그로서 가치가 없다. |
|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

## **10.3 조회 화면**

- GET /api/v1/admin/audit-logs — 대표 전용. 필터: 기간, actor,
  effective, client_id, action, 대행 여부

- 고객 상세 화면에 "변경 이력" 탭 — 해당 client_id의 로그를 시간

## **10.4 보존과 성능**

- 보존 기간은 최소 1년으로 하고, 기간 경과분은 월 단위 배치로 아카이브

> SELECT COUNT(\*) FROM clients c
>
> LEFT JOIN users u ON u.id = c.user_id WHERE u.id IS NULL;
>
> -- 3) 고아 은퇴 프로필
>
> SELECT COUNT(\*) FROM customer_retirement_profiles p
>
> LEFT JOIN clients c ON c.id = p.customer_id WHERE c.id IS NULL;
>
> -- 4) 고아 예수금 계좌 (문제 A — FK가 없어 가장 위험)
>
> SELECT COUNT(\*) FROM deposit_accounts d
>
> LEFT JOIN clients c ON c.id = d.customer_id WHERE c.id IS NULL;
>
> -- 5) 계좌 → 고객 연결 확인
>
> SELECT COUNT(\*) FROM client_accounts a
>
> LEFT JOIN clients c ON c.id = a.client_id WHERE c.id IS NULL;

## **12.2 role 백필 순서**

순서를 지키지 않으면 기존 대표 계정이 매니저로 강등되어 모든 데이터가
화면에서 사라진다. 반드시 아래 순서로 작성한다.

> \# alembic upgrade() 내부
>
> \# (1) 컬럼을 owner 기본값으로 추가 — 기존 행은 전부 대표다
>
> op.add_column("users", sa.Column("role", sa.String(20),
>
> nullable=False, server_default="owner"))
>
> \# (2) 신규 가입자를 위해 기본값을 manager로 교체
>
> op.alter_column("users", "role", server_default="manager")
>
> \# (3) 인덱스
>
> op.create_index("ix_users_role", "users", \["role"\])
>
> \# downgrade()
>
> op.drop_index("ix_users_role", table_name="users")
>
> op.drop_column("users", "role")

| **검증** 마이그레이션 직후 SELECT role, COUNT(\*) FROM users GROUP BY role 결과가 owner = 기존 계정 수, manager = 0 이어야 한다. 이 값이 다르면 즉시 downgrade한다. |
|---------------------------------------------------------------------------------------------------------------------------------------------------------------------|

## **12.3 롤백 계획**

1.  배포 전 DB 전체 백업 (pg_dump). 백업 파일명과 시각을 릴리스 노트에
    기록.

2.  문제 발생 시 alembic downgrade -1 을 3개 리비전에 대해 역순 실행.

3.  코드는 직전 태그로 롤백. role 컬럼이 남아 있어도 구 코드는 이를 읽지
    않으므로 동작에 지장이 없다. 즉 코드 롤백만으로도 즉시 복구가
    가능하도록 컬럼 추가를 비파괴적으로 설계했다.

4.  audit_logs·client_transfers는 데이터 손실 없이 남겨 두어도 무방하다.

## **12.4 첫 매니저 온보딩**

1.  대표가 /admin/managers에서 계정을 생성한다.

2.  테스트 고객 1~2명을 해당 매니저로 이관한다.

3.  매니저 계정으로 로그인해 자기 고객만 보이는지, 다른 고객 ID를 URL에
    직접 넣어도 404인지 확인한다.

4.  대표가 대행 로그인해 배너·복귀·감사 로그를 확인한다.

5.  이상이 없으면 나머지 고객을 이관한다.

# **15. 하지 말 것**

- **권한 조건문을 라우터·서비스에 흩뿌리지 않는다.** permissions.py
  외부에 role 비교가 등장하면 리뷰에서 반려한다.

- **권한 없는 리소스에 403을 반환하지 않는다.** 리소스 은닉은 404, 기능
  차단은 403이라는 구분을 지킨다.

- **조회 후 비교 방식을 쓰지 않는다.** 쿼리에 소유 조건을 걸어 조회한다.

- **is_superuser를 역할로 재해석하지 않는다.** 기존 컬럼은 그대로 두고
  role만 사용한다.

- **매니저 비밀번호를 대표가 알 수 있는 흐름을 만들지 않는다.** 초기
  발급 임시 비밀번호도 저장하지 않고 1회 노출로 끝낸다.

- **중첩 대행을 허용하지 않는다.** 대행 중 다른 계정으로의 전환은
  차단한다.

- **세분화된 권한 매트릭스를 추가하지 않는다.** "매니저B는 조회만" 같은
  요구가 들어와도 본 작업 범위에서는 구현하지 않는다. 규칙이 둘 이상이
  되는 순간 이 설계의 이점이 사라진다.

- **배너 없이 대행 기능을 배포하지 않는다.** 7.4절 참조.

- **감사 로그에 actor만 또는 effective만 기록하지 않는다.** 10.2절 참조.

- **Phase 2 완료 전에 매니저 계정을 만들지 않는다.** 권한 게이트가
  절반만 적용된 상태에서 계정이 생기면 그 시점부터 데이터가 노출된다.
